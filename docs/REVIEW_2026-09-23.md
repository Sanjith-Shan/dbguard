# Integration review, 2026-09-23 (read-only, before the first real fleet run)

Scope: the contract in docs/INTERFACES.md, the spec sections "The system", "Failover",
"Rejoin" and "Experiments", and all of dbguard/agent, dbguard/manager, dbguard/harness,
dbguard/cli, dbguard/mysqlx*.py, dbguard/config.py, bin/*, deploy/*. Reviewed at commit
4683070 (my.cnf with 16 applier workers, self-fence lease, detector majority over
witnesses and the apply-lag rule from 2b6ecb7). I read the code only. Docker was not run.

Tooling at review time: `pytest -q` gave **165 passed in 35.9 s**, and `ruff check .` gave
**All checks passed!**

Severity: **blocker** means the first real run fails or its numbers are wrong. **bug** means
wrong behaviour in a realistic case. **risk** means it could break and needs checking
against the live fleet. **nit** is small.

## What checked out (no finding)

- Agent routes, bodies and response keys match what the manager and harness send and read:
  `/fence` method/gtid_executed, `/promote` gtid_executed, `/repoint {"source"}`,
  `/rebuild {"donor"}` with bytes and phantom_gtids, `/configure {"semisync": bool}`. The
  `/status` shape matches the contract, including the replica sub-object, semisync,
  heartbeat and self_fence. `NodeView.from_status` handles null everywhere.
- Event types, `rejoin.branch` values (repoint/rebuild/manual/none), `rejoin.node`, and the
  `clone` fields (bytes, duration_s, mb_per_s, donor) agree between events.py, the manager
  and chaos.py. `/v1/events?rs=&since=` matches (`ts > since`).
- Workload summary and checker verdict keys match INTERFACES.md and `checker_fields()`.
  Checker exits 0 only when all four properties hold. The no-phantom rule is exactly
  "acked OR an error on that exact seq" (checker.py:111-121). The workload records an error
  row for the in-flight seq before it reconnects, and records in-flight seqs at shutdown.
- MySQL 8.4 syntax: `RESET REPLICA ALL`, `CHANGE REPLICATION SOURCE TO ... SOURCE_SSL=1`
  (the port is an unquoted int), `rpl_semi_sync_{source,replica}_enabled`,
  `clone_valid_donor_list='host:3306'`, and
  `CLONE INSTANCE FROM 'dbguard'@'mysql-a2':3306 IDENTIFIED BY ... REQUIRE SSL`. Status
  columns and variables (`Replica_IO_Running`, `Retrieved_Gtid_Set`,
  `Seconds_Behind_Source`, `Source_Host`, `Rpl_semi_sync_source_{status,clients,
  tx_avg_wait_time,wait_sessions}`, `Rpl_semi_sync_replica_status`) are correct. Nothing
  uses `SET PERSIST`, so a killed node always reboots read-only from my.cnf. No legacy
  `SLAVE`/`MASTER` statements. The TLS decision is applied everywhere: agent db.py,
  mysqlx, mysqlx_sync (workload, checker, bin/bootstrap), manager probe, and chaos `sql()`.
- Promote order: semi-sync source goes ON before `super_read_only=0`, and the fence flag
  is cleared last. The fence sets the flag, fsyncs it, then runs SQL. `/primary` checks
  the flag before and after SQL, and waits for the wake guard after a gap.
- HALTED is sticky (state.py:53). Only `POST /resume` leaves it, and nothing in the
  manager or harness calls it. The harness `heal()` turns HALTED into a hard reset (a
  fresh manager), which it records in `heal.hard_reset`.
- Env names: compose, entrypoint.sh and settings.py all use DBGUARD_NODE, DBGUARD_RS,
  DBGUARD_SERVER_ID, DBGUARD_SEMISYNC, DBGUARD_MANAGER_URL and MYSQL_ROOT_PASSWORD. The
  state volume is at /var/lib/dbguard and the fence file at /var/lib/dbguard/fenced. The
  manager image has the docker CLI and compose plugin, and compose mounts the socket.
- In the entrypoint exec chain, `python3` resolves to the venv because PATH puts
  /opt/dbguard/bin first. The chain is tini, then entrypoint.sh, then
  `exec dbguard-agent`. The agent spawns `docker-entrypoint.sh mysqld`, which gosu-execs
  into mysqld, so the child pid is mysqld's and `MYSQLD_PARENT_PID == getppid()`.
- Experiment 4 does not fire the self-fence lease: the replicas are fine, so
  `Rpl_semi_sync_source_clients` stays at 2 and resets the timer (core.py:796-800).

## Findings

### 1. The harness's failover_s can be ~0 s because an ack of a pre-crash write lands after the first error. blocker
`dbguard/harness/chaos.py:209-215, 227-228`. `first_ok_after_ts` is the first `t_ok`
greater than the first `t_err`. Eight client threads take their timestamps independently.
When the primary is killed, one client's INSERT fails at inject+2 ms. Another client's
INSERT committed a moment before the kill, but its thread records `t_ok` at inject+3 ms.
failover_s then comes out as 0.003 s. This is likely in Experiment 1 (the headline
number). It also breaks the contract definition "first successful write through HAProxy
after the failure".
Fix: count only an ok whose request started after the first error,
`t_ok - latency_ms/1000 >= first_error_ts`. Better still, count only an ok on a connection
opened after that client's own error (log a `reconnect` flag or connection id in the ack
row). Apply the same rule to the workload summary's `first_ok_after_error_ts`
(workload.py:198-201).

### 2. Hang runs longer than rebuild_after_s provision and clone the spare mid-run. blocker
`dbguard/manager/controller.py:216-217`, `replacement.py:83-93`, `chaos.py:1042,1073`.
After a failover the set is DEGRADED, because the old primary is not a replica, and
`unhealthy_since` is the failover time. The hang scenarios keep the old primary frozen for
`hang_seconds=90`, which is more than `rebuild_after_s=60`. So about 66 s into every
hang-container and hang-process run, the manager runs `docker compose up mysql-a4`,
clones it from the surviving replica, and appends it to `ctl.members`. The list only
grows and is never undone unless there is a hard reset. Effects:
- The clone I/O overlaps the woken-primary measurement.
- mysql-a4 stays a member for later runs, so kill-two and the checker's node list change.
- `sc_replica_loss` later finds the spare already running.

Fix, in one of these ways:
- Replace only nodes that have been unreachable (not merely non-replicating) for
  `rebuild_after_s`, and never count a former primary that is merely down.
- Or have the harness set `hang_seconds < rebuild_after_s`, or a larger
  `rebuild_after_s` for those scenarios.

Either way, the harness must remove the spare from the set in heal (today only a hard
reset does).

### 3. The manager's 1.0 s /status timeout is tighter than the agent's own worst case, so witnesses and candidates vanish under load. bug
`dbguard/manager/client.py:97` (`status_timeout_s=1.0`), also `failover.py:60` and the
`fresh_views` calls. The agent's `/status` connects with a 1 s budget, runs five queries
with a 1 s timeout each, and then makes a 500 ms TCP probe of the source (core.py:315-322).

In Experiment 3 the primary DROPs every packet from the replicas. So every replica's
`tcp_reachable` burns the full 0.5 s. On a loaded Docker Desktop VM, `/status` then
approaches or exceeds 1.0 s. A replica whose `/status` times out is not a witness
(detector.py:63) and not a candidate (`"agent unreachable"`, selection.py:34-35).

Results:
- With both replicas slow, `witnesses=0` and the verdict stays SUSPECT forever.
- If `choose()` sees them slow, the set HALTs with "no promotable replica".

Fix:
- Raise the manager's status timeout to 2.5 to 3 s. The loop is concurrent, so this does
  not slow detection.
- Make the agent's `/status` return within 1 s total. Run the TCP probe concurrently with
  the SQL, and give the whole collect one deadline instead of one per query.

### 4. A fence-by-kill restarts mysqld at once, and replicas still pointed at it re-fetch its unacked tail before they are repointed. bug
`dbguard/agent/core.py:377-390` with `supervisor.py:116-119` (`_immediate`), and
`dbguard/manager/failover.py:133-186`. After `SIGKILL` the supervisor restarts mysqld with
no backoff. The old primary comes back read-only but still serves binlogs. It holds the
transactions that were binlogged but waiting for an ack, which crash recovery commits.

The replicas' IO threads, with `SOURCE_CONNECT_RETRY=1`, reconnect to it and pull those
transactions. That happens while the manager is choosing, catching up and repointing.
- If the winner is already promoted and only the loser gets them, the loser holds GTIDs
  the new primary never had, and auto-position will not remove them. That is silent
  divergence, and the checker reports it as not converged.
- If they reach the winner during catch-up, the subset check passed on a snapshot that
  no longer holds.

This is realistic in hang-process (the agent is alive, so the fence is always "kill") and
in partition-replicas after the iptables flush, if a replica was not repointed.

Fix (orchestrator does this): in dbguard mode, `STOP REPLICA IO_THREAD` on every candidate
before `choose()`, and repoint them afterwards. Also, after a kill fence, hold the
restarted mysqld until the manager has rejoined the node, for example by starting it with
`--skip-replica-start --skip-networking`, or by not restarting on the fence path until
`/unfence` or `/repoint`.

### 5. The checker never looks at the old primary, so split brain from a woken or naive old primary is invisible to single_writer. bug
`dbguard/harness/chaos.py:974`. `check(run, wl, [n for n in f.members() if n != old ...])`
drops the one node that can violate single-writer. In naive hang-process the old primary
wakes writable, its agent answers `/primary` 200, and HAProxy sends traffic to two
backends. `single_writer_violations` still reads 0. `writes_on_woken_primary` covers the
hang runs only partly, and only counts rows missing from the new primary.
Fix:
- Include the old primary in the checker's single-writer pass whenever it is reachable.
  It is fine to leave it out of convergence and lossless, or to converge only after the
  rejoin.
- Also sample single-writer during the run, since the spec says "at every checkpoint".
  For example, poll `agent_primaries()` every 1 s.

### 6. The naive baseline can silently run with semi-sync on, and it still fences second writers. bug
- `dbguard/harness/chaos.py:1351-1360`: `verify_mode` checks only the manager's mode. A
  fleet started with `DBGUARD_MODE=naive` but without `DBGUARD_SEMISYNC=0`, for example a
  node recreated from a shell that pin_compose_env did not cover, runs semi-sync
  AFTER_SYNC. It then loses zero acked writes, which is exactly what the spec says must
  never pass unnoticed.
  Fix: in `verify_mode`, read `/status` on every node and require
  `semisync.source_enabled == false and replica_enabled == false` in naive mode, and the
  primary's `source_enabled == true` in dbguard mode. Record `semisync_effective` on every
  row, not only in cost.
- `dbguard/manager/rejoin.py:64-74`: `rejoin_actions` fences any second writable node in
  every mode. Naive mode is specified as "no fence". This fence makes the naive
  woken-primary and split-brain numbers look better than a naive tool.
  Fix: skip it when `ctl.mode == "naive"`, or record in the event that naive borrowed
  DBGuard's second-writer fence.
- Risk: with a sub-millisecond replica lag on one host, async replication can lose 0 writes
  in many naive kill runs. Promotion does run `STOP REPLICA` without waiting for catch-up,
  which helps. If naive loses 0, add `tc netem delay 2ms` on the replicas for naive kill
  runs, as the spec asks ("fix the harness until the baseline loses writes"), and record it
  in the row.

### 7. make up races the manager's auto-bootstrap against bin/bootstrap. bug
`Makefile` `up:`/`up-naive:` and `dbguard/manager/bootstrap.py:43-49`. The manager
container starts with the fleet. It bootstraps a set as soon as all three members answer,
are read-only and have equal GTIDs. `bin/bootstrap` waits for all six mysqld and then does
the same with direct SQL. The last set to come up (usually rs2) gets both at once. The two
run concurrent `STOP REPLICA`/`CHANGE REPLICATION SOURCE`/`START REPLICA` on the same
nodes, so one side gets ER 3021 or 3081:
- If bin/bootstrap loses, `make up` exits non-zero.
- If the manager loses, the repoint is retried 10 s later.

Fix: the manager owns bootstrap now, so `make up` should wait for
`GET /v1/sets/*` to show a primary instead of calling bin/bootstrap. Or bin/bootstrap should
exit early when the manager answers `/v1/status`. Keep bin/bootstrap for orchestrator mode
only (hard_reset already does that).

### 8. Role changes on the agent do not retry a pooled link that a fence killed. bug
`dbguard/agent/core.py:429, 455, 481` (`promote`, `repoint`, `configure` use
`self.db.session()` directly). Only `_sql()` retries once on 2006/2013. A `/status`
connection that is checked out during a fence is on the kill list. It is not the fence's
own connection, and its user is dbguard. If that `/status` finishes between the thread
list and the `KILL`, it goes back to the idle pool with a dead thread. The next
`/promote` on that node fails with "Lost connection" (500). The switchover abort path
(switchover.py:88-93, promote the old primary back) then HALTs the set. A rejoin repoint
of the fenced old primary fails and waits the 10 s backoff.
Fix: run the role-change bodies through `_sql`-style retry-on-2013. A retry is safe
because every step is idempotent. Or ping pooled sessions before role SQL, or skip the
agent's own `program_name='dbguard-agent'` threads in `CLIENT_THREADS_SQL` (join
`performance_schema.session_connect_attrs`).

### 9. Catch-up can never finish when the dead source left a partial transaction in the relay log. risk
`dbguard/manager/failover.py:65` and `model.py:144-145`. `relay_applied` requires
`Retrieved_Gtid_Set ⊆ gtid_executed`. When the source dies mid-send, the IO thread can
have the GTID of a transaction it did not fully receive. With the IO thread stuck in
Connecting, that GTID stays in the retrieved set and is never applied. The result is a
30 s catch-up, then HALTED, on a plain kill. Probability per run is low, but Experiment 1
runs 30 times in three modes.
Fix: treat the winner as caught up when `Replica_SQL_Running_State` is "Replica has read
all relay log; waiting for more updates" (add it to `/status`). Or accept a retrieved minus
executed of exactly one trailing GTID while the IO thread is not Yes, and note it in the
event.

### 10. Rejoin and the second-writer fence run inside the poll tick, so detection pauses for up to 30 s. risk
`dbguard/manager/controller.py:150-181` and `rejoin.py:68, 101`. `rejoin_actions` awaits
`/repoint` (timeout 30 s) and `/fence` (3 s) inline, under `ctl.lock`. During that time the
set is neither polled nor evaluated. A slow repoint of a rejoining node right after a
failover therefore blinds detection of a second failure in the same set.
Fix: run repoints through `start_maintenance`, or give them a short timeout (5 s) and let
the backoff retry.

### 11. Event queries compare the host clock with the Docker VM clock. risk
`dbguard/harness/chaos.py:477-478, 879, 970, 1128, 1367`. Event `ts` comes from the
manager container (Linux VM clock). The filter uses `inject_ts - 1` and `t_restart - 1`
from the macOS host clock. After a laptop sleep, the Docker Desktop VM can drift by more
than 1 s. The failover event then gets filtered out, the row says "no failover event
found", `rejoin` is null, and `rs2_state_changes` undercounts.
Fix: measure the offset once per run by comparing `GET /v1/status` with a local timestamp
(add a `now` field to /v1/status), or widen the margin to 30 s and match on
`old_primary`. failover_s itself is safe, because it uses only host clocks.

### 12. The orchestrator baseline runs with DBGuard's self-fence lease and wake guard active. risk
`deploy/docker-compose.yml:31-35` and `dbguard/agent/core.py:741-742`. In orchestrator mode
the harness stops the `dbguard` container but leaves `DBGUARD_MANAGER_URL` set on the
nodes. Two things follow:
- A primary with 0 semi-sync clients self-fences after 10 s. For example, the woken old
  primary in hang-container, whose replicas Orchestrator repointed.
- The startup guard fences on a leftover fence file.

Both make Orchestrator's woken-primary and split-brain numbers look better than
Orchestrator alone would.
Fix: for the orchestrator campaign, recreate the nodes with `DBGUARD_SELF_FENCE_AFTER_S=0`,
or have the agent disable the lease when the manager has never been reachable since the
agent started. Note the choice in the rows.

### 13. hard_reset names the spare without its profile. risk
`dbguard/harness/chaos.py:602-604` and `docker.py:146`. `docker compose rm -sfv mysql-a1
mysql-a2 mysql-a3 mysql-a4` runs without `--profile spare`. Depending on the Compose
version, a service in an inactive profile named on the command line is either activated or
rejected with "no such service". `_run(check=True)` then raises and the whole hard reset
fails.
Fix: pass `profiles=("spare",)` to `docker.rm` and `docker.up` wherever the spare is named.

### 14. The ComposeProvisioner inside the manager container resolves the project relative to /deploy. risk
`dbguard/manager/replacement.py:62-66` and `deploy/docker-compose.yml:14-17,159,178-179`. The
manager runs `docker compose -f /deploy/docker-compose.yml -p dbguard --profile spare up -d
--no-recreate mysql-a4`. Compose loads the whole file there:
- `build.context: ..` becomes `/`.
- `./haproxy/haproxy.cfg` and `./fleet.yaml` become `/deploy/...` paths that do not exist
  on the Docker host.

Starting only the spare should not touch those, because the spares have no bind mounts,
and the image already exists so compose does not build. The project `working_dir` label on
mysql-a4 will still differ from the host's, and any later host-side `docker compose up` of
the spare may decide to recreate it.
Fix (cheap and robust): mount the repo's deploy/ directory at its host absolute path. Pass
`--project-directory <host path of deploy>` via env, or add `pull_policy: never` and
`build` only on one service. Test `make up && docker exec dbguard docker compose ... up -d
mysql-a4` once before Experiment 6.

### 15. The heartbeat loop is not gated by the wake guard. nit
`dbguard/agent/core.py:710-728`. After `docker unpause`, the heartbeat task can run its
`SELECT @@super_read_only` (still 0) and send an INSERT before the ticker or `/primary`
has triggered the wake guard. With semi-sync the INSERT is binlogged but never acked, so
it adds a phantom GTID on the woken node. No client write is affected, and HAProxy stays
safe because `/primary` waits for the guard. It does push rejoins toward the rebuild
branch, and Experiment 1 reports that branch count.
Fix: in `_heartbeat`, compute the monotonic gap itself, or skip while `_guard_task` is
running or a gap is pending.

### 16. The wake guard fences a legitimate primary while the manager is still discovering. nit
`dbguard/agent/core.py:657-663` and `manager/api.py:49`. Right after a manager restart (the
harness restarts it on every hard reset), `/v1/sets/rs2/primary` answers
`{"primary": null}` until `discover()` runs. An rs2 agent that restarts or thaws in that
window fences a healthy writable primary.
Fix: have the manager return 503 (unknown) until discovery ran, and have the agent treat
503 like "unreachable", which falls back to the fence-file rule.

### 17. Timeout mismatches between the manager and the agent. nit
- `failover.py:171`: `/promote` gets 30 s from the manager, but the agent allows 30 s per
  statement (`role_change_timeout_s`, 6 statements). The manager can declare the promote
  failed and HALT while the agent finishes it, leaving a writable node that the manager
  does not know is primary. The second-writer fence recovers this, but it is noisy.
  Align the budgets, for example agent total 20 s and manager 30 s.
- The node `stop_grace_period: 30s` is shorter than `MysqldSupervisor.stop(120 s)`. Under
  load, docker SIGKILLs mysqld on `docker compose stop`. It is harmless with
  `innodb_flush_log_at_trx_commit=1`, but it looks like a crash in the error log.

### 18. First-boot items (item 9 of the brief). ok, with notes
- The `super_read_only=1` versus init SQL trap is handled: `dbguard-initdb.sh` starts the
  temporary server with `--super-read-only=OFF --read-only=OFF` and runs 01, 02 and 99 in
  order. `99-reset-gtids.sql` wipes anything the image's own setup binlogged. docs/BUGS.md
  records the fleet has already booted this way, and `mysqld --initialize` ignoring
  `plugin_load_add` is why the `loose_` prefixes are there.
- `plugin_load_add` on one line per plugin is valid syntax.
- `docker compose up` has no `depends_on`, so the manager can start before the nodes. That
  is fine: `discover()` waits, and the agents' startup guard "leaves" when the manager is
  unreachable and there is no fence file.
- Risk: the Dockerfile fetches tini from GitHub at build time. Offline builds fail. That is
  acceptable, but it is noted.

## Top 5 by likelihood of breaking the first real failover

1. **#1 failover_s race.** It will produce near-zero failover times in some kill runs, and
   those runs will look like successes.
2. **#3 the 1.0 s status timeout.** With replicas slow under load or behind an iptables DROP,
   witnesses and candidates disappear. The result is SUSPECT forever or HALTED with "no
   promotable replica".
3. **#2 hang runs trigger a spare replacement.** Every Experiment 2 run provisions and
   clones mysql-a4 mid-measurement, and the set's membership drifts across runs.
4. **#7 make up bootstrap race.** The first `make up` can fail or leave rs2 half
   configured before any failover is attempted.
5. **#4 kill fence restart and replica re-fetch** (with #9 partial-trx catch-up as runner-up).
   It gives silent divergence or a spurious HALT on hang-process and plain kill runs.
